# Monday.com API reference

Endpoint reference for the Monday.com GraphQL API. This is the *connection doc* for the task-tracking tool in the Sturdy Ai stack — keep it current. When a call fails and you work out why, fix it here so the same mistake never happens twice.

> **Why API over MCP here:** GraphQL lets you request exactly the fields you need, so it's token-lean. The Monday MCP also exists and is quicker to wire — use that for your own live AIOS if it's already connected; teach/ship this doc for portable, low-context client builds.

---

## 🔑 Get your key (plain English — for the setup wizard)

1. Go to **https://monday.com** and sign in.
2. Click your **avatar** (bottom-left) → **Developers**.
3. Open **My Access Tokens** → copy your token.
4. Paste it here — I'll add it to your `.env` and verify.

## Connection

| | |
|---|---|
| **Endpoint** | `https://api.monday.com/v2` (single endpoint, all queries POST here) |
| **Method** | `POST` |
| **Protocol** | GraphQL (not REST — you send a `query`/`mutation` string) |
| **Auth header** | `Authorization: <MONDAY_API_TOKEN>` |
| **Content type** | `Content-Type: application/json` |
| **Version header** | `API-Version: 2024-10` (pin a version; Monday rolls versions and deprecates old ones) |

**Env vars** (in `.env`, gitignored — never commit):
```
MONDAY_API_TOKEN=   # personal token: avatar (bottom-left) > Developers > My Access Tokens
MONDAY_BOARD_ID=    # the primary board you operate on
```

**Minimal request shape** (HTTP body):
```json
{ "query": "query { me { id name email } }" }
```
Pass GraphQL `variables` as a second JSON field to avoid string-escaping hell:
```json
{ "query": "query ($b: ID!) { boards(ids: [$b]) { name } }", "variables": { "b": 123456 } }
```

## Core objects (the mental model)

- **Account** → has **Workspaces** → have **Boards** → have **Groups** (the coloured row sections) → have **Items** (rows) → have **Subitems** and **Updates** (the comment thread).
- Each Item has **Column values**, keyed by `column_id` (the column's stable id, *not* its display title). Get column ids once from the board and reuse them.
- **Users** and **Teams** are account-level.

## Common queries (reads)

**Who am I / test the token**
```graphql
query { me { id name email } }
```

**List boards (and their columns — do this once to learn column ids)**
```graphql
query {
  boards (ids: [123456]) {
    id name
    columns { id title type }
    groups { id title }
  }
}
```

**Get items on a board (paginated — `items_page` is the current way)**
```graphql
query {
  boards (ids: [123456]) {
    items_page (limit: 50) {
      cursor
      items { id name
        column_values { id text value }
      }
    }
  }
}
```
- `value` is the raw JSON for the column; `text` is the human-readable rendering. Prefer `text` for display, `value` when you need structured data.
- Next page: pass the returned `cursor` to `next_items_page (limit: 50, cursor: "...")`.

**Filter items by column value** (e.g. all items where Status = Done)
```graphql
query {
  items_page_by_column_values (
    board_id: 123456,
    columns: [{ column_id: "status", column_values: ["Done"] }]
  ) {
    cursor
    items { id name }
  }
}
```

**Workload snapshot across people** (read the People column + Status)
```graphql
query {
  boards (ids: [123456]) {
    items_page (limit: 100) {
      items {
        name
        column_values (ids: ["person", "status", "date"]) { id text }
      }
    }
  }
}
```

**List users**
```graphql
query { users (kind: non_guests) { id name email is_admin } }
```

## Common mutations (writes)

> Default the AI account to **read-only** until write access is genuinely needed. When it writes, it acts as the dedicated "Sturdy Ai" Monday user — never your personal login.

**Create an item**
```graphql
mutation {
  create_item (
    board_id: 123456,
    group_id: "topics",
    item_name: "New task from AIOS",
    column_values: "{\"status\":{\"label\":\"Working on it\"},\"date\":{\"date\":\"2026-06-30\"}}"
  ) { id }
}
```
`column_values` is a **JSON string** (note the escaped quotes). See formats below.

**Update several column values at once**
```graphql
mutation {
  change_multiple_column_values (
    board_id: 123456,
    item_id: 987654,
    column_values: "{\"status\":{\"label\":\"Done\"},\"numbers\":\"42\"}"
  ) { id }
}
```

**Post an update (comment) on an item**
```graphql
mutation { create_update (item_id: 987654, body: "Auto-generated by the AIOS morning routine.") { id } }
```

**Create a subitem**
```graphql
mutation { create_subitem (parent_item_id: 987654, item_name: "Sub-step") { id } }
```

**Move an item to another group**
```graphql
mutation { move_item_to_group (item_id: 987654, group_id: "done_group") { id } }
```

**Archive / delete an item**
```graphql
mutation { archive_item (item_id: 987654) { id } }
mutation { delete_item  (item_id: 987654) { id } }
```

## Column value JSON formats (the part that bites you)

`column_values` maps `column_id` → a typed value. Common types:

| Column type | JSON to send |
|---|---|
| Text | `{"text_col_id": "Sample text"}` |
| Long text | `{"long_text": {"text": "Sample"}}` |
| Status | `{"status": {"label": "Done"}}` or by index `{"status": {"index": 1}}` |
| Date | `{"date": {"date": "2026-06-30"}}` (optional `"time": "13:00:00"`) |
| Numbers | `{"numbers": "42"}` (string) |
| People | `{"person": {"personsAndTeams": [{"id": 12345, "kind": "person"}]}}` |
| Dropdown | `{"dropdown": {"labels": ["Option A", "Option B"]}}` |
| Checkbox | `{"checkbox": {"checked": "true"}}` |
| Link | `{"link": {"url": "https://…", "text": "Label"}}` |
| Email | `{"email": {"email": "a@b.com", "text": "a@b.com"}}` |

Gotchas:
- Status/Dropdown labels must match an **existing** label on that column exactly (case-sensitive), or use the numeric `index`.
- The whole `column_values` argument is a JSON *string*, so every inner quote is escaped. Build it with `variables` (a `JSON!` type) where possible to avoid double-escaping.

## Pagination

- `items_page (limit: N)` returns up to `N` items plus a `cursor`.
- Keep calling `next_items_page (limit: N, cursor: "<cursor>")` until `cursor` comes back `null`.
- Max `limit` is 500; 25–100 is the sweet spot for complexity budget.

## Webhooks (event-driven cadence)

Create a webhook so a routine fires on Monday events instead of polling:
```graphql
mutation {
  create_webhook (board_id: 123456, url: "https://your-endpoint", event: create_item) { id board_id }
}
```
Useful events: `create_item`, `change_column_value`, `change_status_column_value`, `create_update`, `item_deleted`.

## Rate limits & complexity

- Monday charges by **query complexity**, not flat call count. Each query has a complexity cost; you get a per-minute read budget (in the millions) and a separate write budget.
- Ask for **only the fields you need** — deep nested queries (board → items → column_values → …) burn budget fast.
- Daily call limits also apply by plan tier.
- A `Complexity budget exhausted` error means wait for the reset window (the error states `reset_in_x_seconds`) or slim the query.

## Debugging notes

- GraphQL returns HTTP `200` even on errors — **always check the `errors` array** in the response body, not just the status code.
- `column_id` ≠ column **title**. If a write silently no-ops, you probably used the title. Re-fetch `columns { id title }`.
- "ID" args: Monday now expects `ID`/`[ID!]` types — pass board/item ids as numbers or numeric strings, not quoted unless the schema says so.
- Pin `API-Version`; an un-pinned call can break when Monday promotes a new default version.
